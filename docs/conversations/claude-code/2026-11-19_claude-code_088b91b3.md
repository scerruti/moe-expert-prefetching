### 1. #59: collection can lose rows and still report success (P1)

**Where:** `full_pipeline.py`, in the code that turns a batch's routing into Parquet rows.

**What happens:** before writing, the code drops any row containing a NaN or infinite probability. It logs a warning, but nothing else changes:
- The row count the validator checks is taken *after* the drop, so the count looks consistent.
- `validation_passed` stays `True`, and no error is recorded.

Waleed injected 4 bad rows: 20 of 24 rows were saved and the run reported success.

**Why it matters:** it's the same pattern as the swallowed hook errors he flagged in #111. A run can succeed with data quietly missing, and since this is a research dataset, a gap nobody knows about is worse than a crash. It hasn't happened in our real runs, as the trial collection had no such rows, but nothing would tell us if it did. The skip-with-a-warning behaviour was deliberate, carried over from older validation code, but it contradicts the "fail loudly" rule we've applied everywhere since.

**Fix:** stop the run, or at least mark validation failed and record an error, when any row is dropped. Also check completeness against what *should* exist: every real token of every prompt, at all 24 layers. Add a test that injects bad values and expects the run to fail.

### 2. #59: the batch-variance comparison ignores missing rows (P2)

**Where:** `batch_variance.py`, which produced the #114 statistics.

**What happens:** it compares two orderings by joining their rows on (prompt, token, layer), and an inner join keeps only rows present in **both** files. A row missing from one file just disappears from the comparison. Waleed's example: a 3-row reference against a 2-row result reported 100% bitwise agreement, with no mention of the missing row. Duplicate keys aren't checked either, and a duplicate would make the join count some rows twice.

**Why it matters:** this script produced the #114 numbers. They're very likely fine: my k-scaling script checks that the two files' keys match exactly, and on the same trial data it reproduced `batch_variance.py`'s 2.02% change rate. But the tool itself should refuse mismatched input rather than rely on that.

**Fix:** before comparing, check that keys are unique in each file and identical between them. Report or reject any mismatch, and add a test for each case.

### 3. #58: router hooks can be left attached if tokenization fails (P2)

**Where:** `run_forward_pass_pipeline` in `forward_pass.py`.

**What happens:** it registers the router hooks, then tokenizes, then opens the `try/finally` that removes the hooks. If tokenization raises, for example on a bad prompt, the `finally` never runs and the hooks stay attached to the model. Waleed reproduced it: two hooks were left on the toy model.

**Why it matters:** this function now accepts a model that's already loaded, so the model can be reused. Leftover hooks would keep firing and filling an orphaned buffer. #119's fixture would clean up after a test, but not in normal use. The full collection doesn't go through this function, so the risk is mostly in tests and small runs.

**Fix:** move the tokenization inside the `try`, or register the hooks after tokenizing. Add a test where tokenization fails and check that no hooks remain.

## Turn 10 (16:48)

**User:**

> Binary logistic regression (explain in context)

**Claude:**

**Binary logistic regression** predicts the probability that something is yes rather than no. It takes a weighted sum of input features and squashes it into the range 0 to 1:

```
p(yes | x) = σ(w · x + b),   where σ(z) = 1 / (1 + e^(−z))
```

It's trained by minimising cross-entropy, which rewards confident correct answers and heavily punishes confident wrong ones. The result is a probability, not just a label.

### In the prefetching project
The yes/no question is: **will expert *e* be one of the top 4 at layer *l + H* for this token?**

- **Target:** a 1 for each of the 4 chosen experts and a 0 for the other 56. Each token chooses 4 experts, so this is **multi-label**, not one choice from 60. The usual approach is 60 binary models per target layer, one per expert, often trained together as a single 60-output layer.
- **Inputs:** whatever the predictor can see at layer *l*. With the Phase 1 data, that's the **60 routing probabilities at layer *l***, perhaps with earlier layers and the token ID. One catch: Phase 1 doesn't store hidden states. Using the 2,048-dimensional hidden state as input would need it collected separately.
- **Output:** a probability for each expert. To prefetch, rank the 60 by probability and fetch the top *k + m*. That maps straight onto the Phase 5 metric, Recall@(k+m), and onto the buffer question from the k-scaling work.

### How it compares with the ridge regression from the seminar
- **Ridge regression** predicts *how much*: the routing probabilities themselves, as continuous numbers. You'd then take the top *k + m* of the predictions.
- **Logistic regression** predicts *whether*: the selection itself. That's closer to what prefetching needs, since what matters is fetching the right experts, not predicting a probability of 0.091 precisely.

Both are linear and quick to train, and both make good **baselines**, the floor a neural predictor has to beat. Fitting both would tell you whether predicting probabilities or predicting selections works better.

### Things specific to this data
- **Class imbalance:** only 4 of 60, about 6.7%, are positive. A model that always says "no" is 93% accurate and useless, so judge it by **Recall@(k+m)**, not accuracy. Ranking handles this naturally; a fixed threshold like p > 0.5 doesn't.
- **Noisy labels:** about 2% of decisions change with batch composition, often at exact fp16 ties. So no predictor can reach 100%. The ceiling is about **99.5% recall at m = 0** against labels from a different batching (#114). Report the predictor's recall next to that ceiling.
- **Calibration is a bonus:** logistic regression's probabilities tend to be well calibrated. A predicted 0.3 then really means about a 30% chance, which could be used to choose *m* for each token instead of using a fixed buffer.
- **Interpretability:** each weight shows how strongly expert *i* at layer *l* predicts expert *e* at layer *l + H*. That's essentially a learned version of the layer-to-layer similarity-matrix idea from the seminar.
